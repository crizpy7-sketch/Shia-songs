## Named migration boundary

`202610030001_shia_edge.sql` creates only the private `shia_edge` schema with `requests`, `payments`, `sessions`, `events`, `fulfillment`, `notifications`, and `rate_limits`. All tables have RLS, and PUBLIC/anon/authenticated/service_role direct table privileges are revoked. It does not add public order columns, replace existing triggers/policies, modify inventory objects, reset default ACLs, or query/backfill old orders.

It adds fixed public RPC wrappers `shia_edge_submit`, `shia_edge_request`, `shia_edge_finalize`, `shia_edge_payment_claim`, `shia_edge_payment_reserve`, `shia_edge_payment_save`, `shia_edge_payment_release`, `shia_edge_session`, `shia_edge_event`, `shia_edge_notification_claim`, `shia_edge_notification_finish`, and `shia_edge_rate_limit`. Each uses `SECURITY DEFINER` with an empty search path, explicit object names and no dynamic SQL. PUBLIC/anon/authenticated execution is revoked; only the trusted backend service role receives execution. These wrappers are exposed in the Data API's public schema only so the backend can call them; they are not callable by public browser credentials. There is no generic SQL executor or public customer-data retrieval route.

The separate `shia_edge_admin_payment_status` RPC is granted to authenticated users and verifies the existing `private.shia_is_admin()` membership rule inside the function. It returns only requested order UUIDs, payment state and paid timestamp. It returns no capabilities/hashes or provider/customer details. Existing admin UI adds those labels after v2 cutover and can search the opaque UUID used in alerts. It continues to read original orders and signed photos through the existing membership policies. Merely changing admin production status cannot mark a payment paid.

New private requests reference `public.shia_song_orders`; child financial/outbox records reference those requests. This intentionally prevents deleting a v2 order through the old DELETE grant while its private records remain. There is no current frontend delete button. Approve this retention boundary explicitly, or review an alternative before migration; do not casually cascade-delete financial/outbox state.

`202610030002_shia_revoke_truncate.sql` contains only `REVOKE TRUNCATE ON public.shia_song_orders FROM authenticated` in a transaction. TRUNCATE bypasses RLS, so membership SELECT/UPDATE/DELETE policies cannot protect against the audited grant. Other SHIA privileges and inventory grants/policies are preserved. This is a separate security approval, not an executed correction.

## Durable behavior

Submit hashes the UUID request key and a canonical normalized payload. A unique request key plus a transaction/advisory lock prevents concurrent duplicate rows; different content under the same key conflicts. Original fields, status and numeric order number remain in the existing SHIA table. Submission/payment capabilities are separate HMACs, with only hashes in the private schema. Signed upload paths are persisted with the request, regenerated on retry, and already uploaded files can be recognized after a lost upload response.

Allowed files are the audited bucket/UI intersection: JPEG, PNG, WebP, HEIC, MP4 and QuickTime, at most 20 nonempty files of at most 50 MiB each. `image/heif` is deliberately rejected instead of changing the bucket. Paths/type/size/name, ordered photo role, reference role and captions are checked; storage metadata is verified before finalization. The signed-upload path does not use upsert. This preserves current private storage access and does not add content/malware scanning or a public download route.

Finalize locks the private request and atomically updates the original order manifest, records finalization, queues one inquiry alert and provisions the trusted payment record when checkout is enabled. The capability remains retryable for 30 days; finalized requests reject changed manifests. Notification/provider failure cannot undo customer success. A database/outbox failure rolls back the whole finalize operation. Signed files are outside a PostgreSQL transaction, so existing authorized admin deletion of a storage object can still require operator reconciliation.

Checkout cannot hold a transaction across independent Data API calls. The Edge store therefore claims a two-minute fenced lease and persists the exact attempt/request hash before Stripe creation. Concurrent requests return a retryable conflict. A lost database save retries the same Stripe idempotency key and exact parameters; stale leases cannot save or release a newer lease. Reserved attempts older than 23 hours stop for reconciliation before Stripe's 24-hour idempotency retention can permit a duplicate external session. Verified paid state is rechecked during reservation/save to stop a racing checkout. Changed price/return/secret parameters under an unresolved attempt conflict; do not rotate them blindly while attempts are pending.

Webhook processing retrieves current Stripe session state and verifies order/package, exact USD total, line item/price/quantity and test mode. Event receipt, paid state, one fulfillment handoff record and one paid alert commit atomically. Duplicate events or repeated success events do not duplicate handoffs. Stale failures/expiry cannot replace paid state or overwrite a newer session. The handoff record is not delivery of the songs; existing authorized production status/notes are the manual workflow.

The worker checks provider configuration before claiming. It uses leases, stable keys, sanitized failure codes, capped retry delays and a blocked state after the provider's deduplication window. Alert text includes only kind and opaque order UUID, not customer contacts, stories, photos or payment capabilities. `sent` means provider HTTP acceptance, not inbox delivery. No `onboarding@resend.dev` sender fallback exists in v2. Missing sender/key/recipient leaves delivery inactive and jobs unclaimed; it never marks a skipped email sent.

The rate limiter uses two small shared PostgreSQL budgets (60 intake and 120 checkout requests per minute), rather than trusting spoofable IP/proxy headers. Confirm these operational limits and any additional anti-abuse/edge controls during acceptance. Worker processing is one attempt per invocation; schedule frequently enough for the agreed volume and inspect queue age. Cron/Vault/pg_net availability is not yet verified; no extensions or scheduler jobs have been created.

## Rollback and limits

Before cutover, rollback is simply leaving the frontend on v1 with v2 gates off. After real v2 activity, pause new checkout/intake/worker activation as approved, preserve all private records and reconcile outstanding attempts/events; do not drop the schema, erase payment history, replay old emails or regenerate capabilities. V1 cannot finalize new v2 requests, so keep a controlled v2 recovery path for already submitted requests rather than redirecting those tokens to v1. Retain backups and review any destructive cleanup separately.

Pending browser attempts remain in memory. The navigation warning protects accidental exits but does not provide automatic tab/browser-restart recovery. Existing public v1 source limitations remain until its separately approved retirement/hardening. Supabase gateway deployment, Cron availability, real sender readiness, actual live persistence/delivery and Stripe sandbox/live account readiness are not proved by local tests.
